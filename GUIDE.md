Курс «ИИ для бизнеса». Это методичка к занятию. Читайте её сами и давайте своему ИИ-агенту (в IDE или в браузере): внутри есть готовые промпты. Если что-то не получается, сначала пройдите раздел «Если что-то сломалось», потом спрашивайте преподавателя.

## 0. Как пользоваться этим файлом

1. Откройте файл рядом с IDE. Идите по практикам по порядку: каждая устроена одинаково (цель, шаги, промпт для агента, проверка, типичные ошибки).
2. **Агент в IDE** (Cursor, Copilot, Claude Code и т.п.): положите этот файл в папку проекта (например `GUIDE.md`) и в начале работы напишите:

```

3. **ИИ в браузере** (ChatGPT, Gemini и т.п.): вставьте нужный раздел целиком и добавьте свой вопрос. Если файл большой, вставляйте только текущую практику плюс раздел 2 (архитектура).
4. Не копируйте код агента вслепую. После каждого шага запускайте и проверяйте по чек-листу.

### Ваш backend

Бот не содержит знаний и не обращается к OpenAI напрямую: он отправляет вопросы в тот же backend, который отвечает в чате на вашем сайте. Ключ OpenAI нужен только этому backend.

Перед началом проверьте:

- backend запущен и отвечает (чат на сайте работает или запрос через `curl` возвращает ответ);
- у вас под рукой **один пример запроса и ответа** вашего чата: посмотрите в коде сайта или во вкладке Network браузера. Он понадобится агенту, чтобы подключить бота именно к вашему backend.

Если у вашего чата нет обычного HTTP-эндпоинта (например, он работает только через WebSocket), попросите агента добавить простой эндпоинт `POST /chat`, который принимает сообщение и возвращает ответ.

## 2. Архитектура

Идея: **один AI backend, много каналов**. Telegram и сайт не содержат знаний, они только передают вопрос и показывают ответ.

```
Сайт (ваш чат) ─┐
Telegram ───────┼─→ ваш AI backend (RAG + ключ OpenAI) ─→ ответ клиенту
(другие)        ┘            │
                             ├─→ письмо менеджеру
                             ├─→ чат менеджера в Telegram
                             └─→ журнал диалогов (для аналитики)
```

**Адаптер в боте.** Внутри бота одна функция, через которую идут все обращения к backend:

```
ask_backend(session_id, message) -> {"answer": "Доставка стоит ...", "needs_human": false}
```

Она переводит единый формат бота в формат **вашего** backend и обратно. Адрес, названия полей, заголовки у каждого свои, поэтому при отличиях меняется только этот адаптер.

Пример формата (подставьте свой):

```
POST {BACKEND_URL}/api/chat
Заголовок: Authorization: Bearer <токен>      (если у вас есть авторизация)
Тело:     {"session_id": "tg_123456", "channel": "telegram", "message": "Сколько стоит доставка?"}
Ответ:    {"answer": "Доставка стоит ..."}
```

- `session_id` уникален для диалога: для Telegram берём `tg_<chat_id>`. Если ваш backend хранит историю по идентификатору сессии, он сразу будет помнить контекст диалога.
- `needs_human = true` означает, что нужен менеджер. Если ваш backend такой признак не возвращает, адаптер подставляет `false`, а решение «нужен человек» бот принимает по простым правилам (см. Практику №2а).

**Режимы диалога.** Для каждого `session_id` хранится режим: `bot` или `human`. В режиме `human` бот молчит.

## 3. Правила безопасности

- Секреты (токен Telegram, токен backend, пароли) храните **только** в файле `.env`. В код их не вставляйте.
- Добавьте `.env` в `.gitignore` до первого коммита.
- Никогда не отправляйте ключи в чат с ИИ и не показывайте их на скриншотах.
- Ваш backend использует платный ключ OpenAI: не запускайте бесконечные циклы и массовые автотесты. Для проверки хватит 3–5 вопросов.
- Вызывайте backend только когда это необходимо (см. гибридную схему в Практике №1).
- Письма отправляйте только на свои адреса или адреса людей, которые дали согласие.

Промпт-страховка для агента (добавляйте в начало любого задания):

```
Правила: не выводи и не придумывай секреты, все ключи читай из .env через переменные окружения. Не добавляй циклы и тесты, которые массово вызывают платный ИИ. Если нужно проверить работу, предлагай не больше 5 запросов. Перед удалением или перезаписью файлов спрашивай подтверждение.
```

### Что ломается чаще всего (передайте агенту вместе с заданием)

Половина «ошибок студента» — это не баги логики, а среда. Проверьте до первой строки кода:

- **Один venv на весь проект**, а не на практику. `python3 -m venv .venv` в корне; `pip install --user` на части машин запрещён политикой файловой системы.
- **Библиотека обязана подходить вашей Python.** `python-telegram-bot` 21.x не работает на Python 3.13+ (`RuntimeError: There is no current event loop`), берите `python-telegram-bot>=22`; `aiogram` — 3.x. Просите агента назвать версию, которую он ставит, и проверить её `pip show`.
- **Один экземпляр бота и один сервер.** `EADDRINUSE` на 3456 — сайт уже запущен; 409 от `getUpdates` — бот запущен дважды (в том числе где-то в фоновой задаче агента).
- **Значение `.env` читается до конца строки**: `KEY=value # комментарий` — значением станет `value # комментарий`. Комментарии — только над строкой.
- **Пароль приложения Gmail (16 символов) не содержит пробелов** — из буфера обмена он приходит с пробелами, их надо убрать.
- **`.env` один на проект** и для сайта, и для бота: не пложите второй `.env` в подпапку.

## Практика №1. Гибридный Telegram-бот

**Цель.** Бот в Telegram отвечает на вопросы клиентов. Простые случаи обрабатывают сценарии (if/else, 0 токенов), остальное уходит в ваш AI backend. Новую базу знаний не создаём: используем ту, что уже работает на вашем сайте.

### Шаги

1. Получите токен у **@BotFather** и сохраните в `.env` как `TELEGRAM_BOT_TOKEN`. Туда же добавьте `BACKEND_URL` (и `BACKEND_TOKEN`, если нужен).
2. Выберите библиотеку (одну): `python-telegram-bot` или `aiogram` (Python), либо `grammY`/`telegraf` (JS). Достаточно режима polling: публичный адрес не нужен.
3. Сделайте сценарии без ИИ:
   - `/start`: приветствие и меню с кнопками
   - кнопки: «Цены», «Режим работы», «Связаться с менеджером»
   - готовые тексты ответов (возьмите из того, что знает ваш сайт)
4. Сделайте адаптер `ask_backend` (см. раздел 2): он отправляет вопрос в ваш backend и возвращает `answer` и `needs_human`.
5. Для всех остальных текстовых сообщений вызывайте `ask_backend` и отправляйте `answer` клиенту. Если запрос не удался, отправьте вежливое сообщение об ошибке.
6. Храните последние сообщения диалога в памяти и записывайте каждый обмен в файл `dialogs.jsonl`: они понадобятся в Практиках №2а и №4.

### Типичные ошибки

- Бот молчит: токен неверный или бот не запущен. Проверьте логи и значение в `.env`.
- `RuntimeError: There is no current event loop`: python-telegram-bot 21.x на Python 3.13+. Обновите библиотеку (`python-telegram-bot>=22`).
- `EADDRINUSE: 3456` — сайт уже запущен; `409 Conflict` от `getUpdates` — бот запущен в двух экземплярах. Поднимайте по одному процесса.
- pip поставил пакет «в домашний каталог» или отказался: используйте venv проекта, `--user` на части систем запрещён.
- Ошибка 401/403 от backend: неверный `BACKEND_TOKEN` или не тот заголовок авторизации.
- Ошибка 404/422 от backend: адрес эндпоинта или названия полей в запросе не совпадают с вашим backend. Сверьте адаптер с примером запроса.
- Бот не может достучаться до backend: backend запущен только локально, а бот работает в другом окружении. Запускайте бота на той же машине или опубликуйте backend.
- Бот отвечает дважды: запущено два экземпляра.

## Практика №2а. Передача менеджеру и письмо на почту

**Цель.** Когда вопрос требует участия человека, система определяет это и отправляет менеджеру письмо. Менеджер в этой практике — вы сами: письма приходят на вашу почту.

### Когда нужен человек

- клиент нажал «Связаться с менеджером»
- в сообщении есть намерение оформить заказ (простые ключевые слова: «заказать», «оформить», «купить», «позвоните»)
- backend вернул `needs_human = true` (если ваш backend умеет это делать)
- клиент повторяет вопрос или выражает недовольство

### Шаги

1. Напишите функцию `needs_human(message, backend_response)`, которая применяет простые правила (ключевые слова + поле `needs_human`, если оно есть).
2. Напишите функцию `send_manager_email(session_id, channel, last_messages, question, reason, client)` — три последних аргумента нужны, чтобы письмо было полезным, а не «клиент чего-то захотел».
3. Настройте SMTP. Два простых варианта:
   - **Brevo**: в личном кабинете откройте раздел SMTP & API, возьмите хост, порт, логин и создайте SMTP-ключ (он используется вместо пароля). Адрес отправителя нужно подтвердить (verified sender) в Brevo.
   - **Gmail**: включите двухфакторную защиту и создайте пароль приложения; хост `smtp.gmail.com`, порт 587.
   Mail.ru и Яндекс работают так же (`smtp.yandex.ru`, `smtp.mail.ru`, порт 587, пароль приложения) — код к провайдеру не привязан, всё в `.env`. Поднимать **свой** SMTP-сервер для учебного проекта не стоит: исходящий 25-й порт режут провайдеры, без PTR/SPF/DKIM письма уходят в спам.
4. В письме укажите: канал (источник обращения), идентификатор клиента, **основание** (почему позвали человека), суть вопроса, последние сообщения диалога и **как менеджеру выйти на этого клиента**.
5. Подключите функцию к боту: при срабатывании правила отправьте письмо и сообщите клиенту: «Передал информацию менеджеру — он скоро с вами свяжется».
6. Защитите от спама: одно письмо на диалог не чаще раза в 5 минут.

### Как выглядит письмо (сверьте свой DRY_RUN-вывод)

```
Тема: [Coffee Point] Клиент запросил менеджера: tg_660405782

Источник (канал): Telegram-бот
Диалог: tg_660405782
Время обращения: 05.11.2026 17:10
Основание: клиент сам нажал «Связаться с менеджером»

Клиент:
  - Имя в Telegram: Айгерік Смаул
  - Ник: @PeakPeak

Вопрос клиента:
  Хочу заказать торт на выходных

Как выйти на клиента:
  - Ответить в очереди менеджера: http://127.0.0.1:3456/account — бот сам
    доставит ответ клиенту.
  - Telegram chat_id клиента: 660405782
  - Взять диалог себе: /take tg_660405782, вернуть боту: /release tg_660405782
  - Написать в личную: https://t.me/PeakPeak
```

Тема и порядок строк — на ваш вкус, смысл один: **кого зовём, откуда, о чём спросил, как до него добраться**. Ссылка на очередь менеджера строится из `BACKEND_URL`; если кабинет менеджера по другому адресу — добавьте в `.env` переменную `SITE_URL`.

### Что бот знает о клиенте и что с этим может сделать менеджер

| Данные | Откуда берутся | Чем это менеджеру полезно |
| --- | --- | --- |
| `chat_id` (он же `session_id = tg_<chat_id>`) | есть в каждом апдейте | писать **только боту** (`send_message`): в поиске Telegram числа не ищутся |
| `first_name` + `last_name` | `update.effective_user` | подписать письмо, понять, к кому попал |
| `username` (ник) | `update.effective_user.username`, **если клиент сам его задал** | ссылка `https://t.me/<ник>` — написать в личную, минуя бота |
| Телефон | Telegram его **не отдаёт** | только если клиент сам поделился номером (кнопка `request_contact`) |

Отсюда два ограничения:

- **ник есть не у всех.** Если `username` пустой, выдумывать ссылку нельзя: пишем в письме «ник не задан» и оставляем путь через бота.
- **переписка в обход бота не попадает в журнал.** Менеджер ответил клиенту напрямую — диалог исчез из Практики №2б, а в `dialogs.jsonl` (Практика №4) образуются дыры. Надёжнее отвечать через очередь менеджера.

Это персональные данные: имена и ники клиентов не пишите в `dialogs.jsonl` и не отправляйте никому, кроме менеджера.

Хост, порт, логин, пароль, MANAGER_EMAIL и FROM_EMAIL читаются из .env. На 587 — STARTTLS; если провайдер даёт только 465, поддержи implicit TLS отдельным флагом из .env.
3. Письмо текстовое и отвечает на четыре вопроса: КОГО зовём (client: имя, @username, chat_id), ОТКУДА (канал-источник), ЧТО СПРОСИЛ (question + последние 5 реплик) и КАК СВЯЗАТЬСЯ (ссылка на очередь менеджера, /take <session_id>, а при username — https://t.me/<ник>). FROM при пустом FROM_EMAIL бери из SMTP_USER: Gmail и Яндекс не позволяют писать «от чужого».
4. В обработчике бери профиль клиента из update.effective_user (id, first_name, last_name, username) и пересылай его в письмо. Пустой username — норма: в письме пиши «ник не задан», ссылку не выдумывай.
5. Любая ошибка SMTP — сообщение в лог и False, но ответ клиенту бот обязан выдать: письмо не должно ронять обработчик и ронять диалог.
6. При срабатывании needs_human бот отправляет письмо и сообщает клиенту: «Передал информацию менеджеру — он скоро с вами свяжется». Для одного session_id не отправляй письмо чаще раза в 5 минут.
7. Пока DRY_RUN=true, письмо только печатается в консоль — ничего никуда не уходит.
Ничего не отправляй на реальные адреса, пока DRY_RUN=true, и не проси меня прислать пароль в чат: пароль приложения я вклею в .env сам. Проверка — сначала DRY_RUN, потом одно письмо на мой адрес.
```

### Проверка

- [ ] В режиме DRY_RUN письмо печатается в консоль в нужном формате
- [ ] После настройки SMTP письмо приходит на `MANAGER_EMAIL`
- [ ] Повторное сообщение не создаёт новое письмо в течение 5 минут
- [ ] В письме есть канал-источник, вопрос и подсказка, как связаться с клиентом
- [ ] При `username` клиента в письме есть `https://t.me/<ник>`, без него — нет битой ссылки
- [ ] Офлайн-тест (подменённые `Update` и отправка) проходит без сети и без SMTP

### Типичные ошибки

- «Менеджер не может открыть клиента по `chat_id`»: числа `660405782` в поиске Telegram не находится, писать по нему может только бот. Для человека остаётся два пути — очередь менеджера (бот сам доставит ответ) или `@username`.
- Ссылка `https://t.me/None` или `https://t.me/` в письме: `username` у клиента отсутствует, проверяйте значение перед подстановкой.
- Телефон клиента в письме не появится «сам»: Telegram отдаёт номер только после того, как клиент нажал кнопку `request_contact`.
- Менеджер написал клиенту в личную и диалог пропал из `dialogs.jsonl` — аналитика (Практика №4) и `/dialogs` (Практика №2б) больше его не видят.
- `Authentication failed`: неверный логин или пароль SMTP (в Brevo используется SMTP-ключ, в Gmail пароль приложения, а не пароль от аккаунта).
- Gmail принимает пароль и молчит: пароль приложения из буфера обмена приходит с пробелами (`abcd efgh …`), в `.env` их нужно убрать.
- Письмо не приходит, ошибок нет: адрес отправителя не подтверждён в сервисе (Brevo) или письмо в папке «Спам».
- Значение `.env` с хвостом из `# комментария`: парсер оставляет коммент внутри значения — `DRY_RUN=true # так` это не `true`. Комментарии пишите над строкой.
- Таймаут: порт заблокирован сетью, попробуйте другой порт из списка сервиса.
- Падение бота на `KeyError: SMTP_HOST`: отправка вызывается из обработчика — проверяйте отсутствующие настройки и возвращайте ошибку в лог, а не исключение в клиентский ответ.

## Практика №2б. Менеджер подключается к диалогу в Telegram

**Цель.** Менеджер может зайти в диалог и общаться с клиентом без бота. Вы строите это сами в Telegram-боте: клиентом выступает ваш основной аккаунт, менеджером второй аккаунт или служебная группа.

### Как это устроено

У каждого диалога есть режим:

- `bot`: отвечает backend или сценарии
- `human`: бот молчит, сообщения клиента идут менеджеру, ответы менеджера идут клиенту

Команды менеджера:

- `/take <session_id>`: режим `human`
- `/release <session_id>`: режим `bot`

### Схема с пересылкой

Менеджер не может «зайти» в личный чат клиента с ботом напрямую. Поэтому:

1. Клиент пишет боту, в режиме `human` бот пересылает сообщение менеджеру (в служебный чат или группу) с пометкой `session_id`.
2. Менеджер отвечает на это сообщение через «Ответить» (reply).
3. Бот находит `session_id` по сообщению, на которое ответили, и отправляет текст клиенту.
4. Для клиента это один и тот же чат.

### Где взять «менеджера»

Самый простой путь без второго телефона: создайте группу в Telegram, добавьте туда бота и себя. Это служебный чат менеджера. Его `chat_id` бот может показать по команде `/id` (попросите агента её добавить). Клиентом будет ваш личный чат с ботом.

### Промпт для агента в IDE

```
Мы выполняем Практику №2б из GUIDE.md. Сначала объясни, как в текущем проекте устроен обработчик сообщений: где принять решение о режиме, не придётся ли переставлять проверки. Перед изменением существующих файлов перечисли, что именно изменишь. Затем:
1. Добавь хранилище режимов в памяти и функции set_mode(session_id, mode) и get_mode(session_id); по умолчанию режим bot.
2. В обработчике сообщений: если режим human, не вызывай backend, а пересылай сообщение клиента в чат MANAGER_CHAT_ID (из .env) с текстом, содержащим session_id. Запомни соответствие «id пересланного сообщения → session_id».
3. Добавь обработчик ответов менеджера: если в MANAGER_CHAT_ID пришёл reply на пересланное сообщение, отправь текст клиенту. Реплики менеджера не должны попадать в backend как слова клиента.
4. Добавь команды менеджера /take <session_id> и /release <session_id> (работают только из MANAGER_CHAT_ID), команду /id с chat_id текущего чата и /dialogs со списком активных session_id.
5. Проверка режима должна стоять ДО сценариев и ДО вызова backend.
6. Учти API библиотеки, а не воображай: в python-telegram-bot id сообщения — `Message.id` (не message_id), аргументы команды лежат в `context.args` (у CommandHandler нет параметра pass_args), chat_id группы отрицательный. Проверь по установленной версии, а не по общей памяти.
7. Учти, что чат менеджера не может быть одновременно чатом клиента: сообщения из MANAGER_CHAT_ID — это команды и ответы менеджера, но не реплики клиента.
8. Проверка без платного ИИ: подмени Update и объект Bot фиктивными классами и проверь /take, пересылку, reply менеджера, /release — список маршрутов в dialogs.jsonl должен показать human и manager.
Покажи, как воспроизвести цепочку вручную двумя аккаунтами.
```

### Проверка

- [ ] `/take` переводит диалог в режим `human`, бот перестаёт отвечать клиенту
- [ ] Сообщение клиента приходит в чат менеджера с `session_id`
- [ ] Ответ менеджера доходит до клиента в том же чате
- [ ] `/release` возвращает диалог боту
- [ ] В режиме `human` backend не вызывается и токены не тратятся

### Типичные ошибки

- Бот отвечает вместе с менеджером: проверка режима стоит после вызова backend, а должна быть до.
- Ответ менеджера не доходит: менеджер пишет не reply на пересланное сообщение или бот потерял соответствие после перезапуска (хранится в памяти).
- Бот не видит сообщения в группе: убедитесь, что он добавлен в группу, и используйте reply на его сообщения.
- `AttributeError: object has no attribute 'message_id'`: в python-telegram-bot у сообщения `id`; `message_id` — из другой библиотеки.
- `CommandHandler.__init__() got an unexpected keyword argument 'pass_args'`: аргументы `/take tg_123` PTB кладёт в `context.args` сам.
- Реплики менеджера уходят в backend и тратят токены: чат менеджера надо отсека до маршрутизации, иначе он считается клиентом.
- Один и тот же чат не годится клиенту и менеджеру: `/take` и reply менеджера перестанут отличать клиента от менеджера.
- `MANAGER_CHAT_ID` пустой — и вся ветка молчит: бот не пересылает реплики, `/take` и `/dialogs` не отвечают, при этом ошибок в логе нет. Проверьте значение в `.env` до отладки логики.
